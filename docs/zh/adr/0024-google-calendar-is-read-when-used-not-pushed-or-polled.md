# Google 日历在使用时读取，既不用变更通知，也不在后台轮询

用 Google Calendar API 读取日历时，只在日程被用到的时候（打开日历界面、显示卡片、模型用工具查看日程）才发起请求。不使用来自 Google 的变更通知（push），也不在后台每隔几分钟轮询一次。因为要接收通知，就需要一个 Google 能送达的公开入口，以及从那里通知用户计算机的长连接，也就等于要架设按用户保存状态的 ASIST 服务器。后台轮询会把 API 的次数上限用在没在看界面的用户身上。这一上限按 Google Cloud 项目整体计算，是每天 100 万次；这个每天的上限即使申请也无法提高（每分钟为项目 1 万次、每个用户 60 次）。每天 100 万次除以用户数，就是一个人可用的次数。

一次使用发出的请求如下：状态确认是日历列表 1 次，读取日程是所选的每个日历各 1 次（每页最多 2500 件）。修改日程为状态确认 1 次、读取修改前的日程及其日历 2 次、写入 1 次，共 4 次。访问 token 的刷新约为每个进程每小时 1 次，token 端点不计入这一上限。日历的颜色不去获取（也不调用 `colors.get`）。因为界面的颜色由主题的颜色决定。

每个用户每分钟的上限已在 Google Cloud Console 的配额中从默认的 600 次下调到 60 次。如果保持 600 次，仅仅一个账号的请求停不下来，一天就会达到 86.4 万次，用掉项目整体每天上限的几乎全部，其他所有用户的日历都会停。60 次的话，一个账号每天最多 8.64 万次，从上面写的一次使用的次数来看，即使连续翻周也够用。对超过上限的请求，ASIST 会告知请求过多、请等待。

## 未采纳的方案

- **用 syncToken 取上次以来的差异。** 取差异也要在每次使用时为每个日历各请求 1 次，次数与指定期间读取没有区别。而且首次同步会读取日历的全部期间（把重复日程逐条展开后的内容），并要在本地一直持有这份副本。ASIST 的读取是按界面上的月、周，卡片上的今天、本周这样的区间来做的，所以按指定区间读取。
- **接收变更通知（push）。** 如上所述，需要公开入口与按用户保存状态的服务器。
- **在后台定期轮询。** 不在使用的时间也消耗上限，用户一多就会达到项目整体每天的上限。

## 已知限制

- 在其他终端或 Google 日历界面上做的修改，要到下次使用日程时才会到达 ASIST。一直开着的日历界面，在重新打开或改变显示期间时重新读取。

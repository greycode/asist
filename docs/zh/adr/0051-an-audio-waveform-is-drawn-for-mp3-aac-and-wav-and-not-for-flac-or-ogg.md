# 音频波形只对 MP3、AAC、WAV 绘制，FLAC 和 OGG 不显示波形只播放

文件卡片在预览页面里生成音频波形。文件从头开始按每次 4 MB 顺序读取，WAV 直接读取采样，MP3 和 AAC（ADTS 的 .aac 与 MPEG-4 的 .m4a）拆成帧后用 WebCodecs 的 AudioDecoder 解码。录音保存为每个等长区间的最大振幅（峰值），峰值每达到 4,096 个就把相邻的两个合并成 1 个，区间长度翻倍。峰值数量不依赖头部给出的长度，也不会超过 4,096 个，所以无论录音多长、头部有多大差异，占用的内存都不变。因此，音频既不设大小上限，也不放其他查看器有的最后一道安全网。送给查看器的只有要绘制的 400 根柱子的高度。FLAC 和 OGG 不显示波形，只做播放。MP3、AAC、WAV 能从帧的头部或 MPEG-4 的采样表自行拆分，但要拆分 FLAC 和 Ogg，就得为各自的格式编写 demuxer 并一直维护。文件卡片里出现的音频中 FLAC 和 OGG 不多，所以不花这份工夫。

## 未采纳的方案

- **FLAC 和 Ogg 也用自制的 demuxer 拆成帧，交给 AudioDecoder。** Chromium 的 AudioDecoder 能解码 FLAC、Vorbis 和 Opus，但 FLAC 需要把 STREAMINFO 作为 description 传入（Chrome 154 对没有 description 的配置以“description is required”拒绝），帧的边界要靠同步码和 CRC 去找。Ogg 要把页连起来还原成包，若是 Vorbis 还需要处理第一个头部的包。与为每种格式编写和维护的工作量相比，用得上的场合很少。
- **峰值区间的长度先根据头部给出的录音长度决定。** 头部的长度不可靠。用 ffmpeg 中途截断的 MP3，其 Xing 帧把帧数记为 0，9 秒的录音变成 40 万个峰值，1 小时则是 1.59 亿个峰值。把长录音接在短音频后面的 MP3 会保持短音频的长度，下载到一半的 MP3 会保持整个文件的长度。ADTS 的 AAC 若从第一个帧估算长度，会因 afconvert 写在开头的 13 字节静音帧而变成 26 倍长，画完的波形在 400 根里只有 79～159 根。

## 实测

2026-10-03，Apple M5（内存 32 GB）、headless Chrome 154、demo 的 `npm run demo:viewer-budgets`。在其他工作使负载平均值处于 42～63 时测量。

- 2 小时的 MP3（128 kbps、110 MB），第一根柱子在 395 ms 画出，整个波形在 11.0 秒画完。renderer 的内存最多为 +240 MB，界面线程最长停住 21 ms。1 小时的 m4a（AAC 64 kbps、29 MB）用 3.8 秒增加 +230 MB，1 小时的 WAV（606 MB）用 5.8 秒增加 +253 MB。这些值包含预览页面的 iframe 自身使用的约 160 MB。
- 像以前那样在界面里对整个文件调用 decodeAudioData 时（2026-10-02，负载平均值 18），2 小时的 MP3 到画出为止花了 15.6 秒，renderer 的内存变成 +9,567 MB，界面线程停住 812 ms。1 小时的 WAV 是 +10,494 MB。
- 在 CI 的 macos-latest（2026-10-02）上，画完 2 小时的 MP3 的波形花了 32.7～36.3 秒。

## 已知限制

- FLAC 和 OGG 的卡片上显示“この形式では波形を出しません”。ADPCM 的 WAV、Apple Lossless 这类 AAC 以外的 MPEG-4、Chromium 的解码器不接受的 free format 的 MP3 也是一样。
- 长录音的波形从左向右延伸，画完需要时间。2 小时的 MP3 在这台 Mac 上要花 10 秒多。
- MP3 和 ADTS 的 AAC 在绘制过程中，根据已读取帧的采样数和它占文件多少比例来估算录音长度。比特率中途变化的录音，或开头连续静音的录音，开始读取时的估算会失准，波形的横向长度有时会略微伸缩。画完之后，再按解码出的长度重新绘制。

# 测试运行时把字典里的所有消息换成键，字典的抄写由该测试自身的失败来发现

在测试期间，字典里的所有消息都只剩下写着语言和键的文字（`‹ja-JP common.save›`）、占位符和换行符。检查界面上用词的测试用 `t('key')` 从字典读取，所以原样通过。抄写了字典文字的测试，会在抄写的地方失败。像交给模型的文本、保存文件的固定形式、测试数据这些不来自字典的文字，不受替换的影响。因为测试里的日语是不是字典里的文字，无法凭拼写判定，只能看这段文字是从哪里来的。同样是“晴れ”，天气卡片的标签就是字典的文字，日本气象厅的数据就是数据。只有检查字典文字本身的测试（`tests/i18n.test.ts`）才读真正的字典。

## 未采纳的方案

- **测试里写的日语只要和字典里的某一条拼写相同就报错。** 以前用的就是这个形式。数据碰巧和字典的文字相同时会被误报，例外清单不断增加。只是在某个界面往字典里加一个词，无关的测试也会失败。另一方面，与数字组合的句子、句子的一部分、以及用 `aria-label` 找按钮的写法，因为拼写对不上而被漏掉了。
- **把按拼写比对的对象缩小到测试 import 的代码所用的键。** 误报会减少，但凭字典内容判断的性质不变，抄了句子一部分的写法仍会被漏掉。
- **只看 `expect(...)` 内部这类与界面文字相比较的位置上的字符串。** 就会漏掉用 `aria-label` 找按钮这类断言之外的抄写。

## 实测

2026-10-05 加入替换时，按拼写比对的检查原本放行的测试里有 28 件失败，全都是字典的抄写（“14ターン”“2件”“1分05秒で完了”、英语的“Done”“Tomorrow”、用日语 `aria-label` 找按钮等）。demo 的数据直接把文件不存在时的错误文本以日语写了进去，也是这时发现的。以前检查的例外清单里的 24 件，都没有受替换的影响。同一天清点，测试里的 `t()` 有 789 处，其中 291 处在断言之外。

## 已知限制

- 用“不存在”来检查抄写文字的测试（`not.toContain('…')`、用日语 `aria-label` 查找再 `toBeNull()`）即使替换也不会失败，会失去意义却照样通过。
- 检查真实文本如何表现的测试，例如查看每种语言的文本在哪里折行的测试，必须在该文件里换回真正的字典才能写。

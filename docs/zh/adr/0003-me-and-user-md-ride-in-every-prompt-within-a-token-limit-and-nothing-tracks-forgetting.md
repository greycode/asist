# 每次对话都带上 me.md 和 user.md 并各自收在 token 上限内，不持有用来遗忘的机制

每次对话的系统提示词都完整带上 `me.md` 和 `user.md`。对话引擎和 Gemini Live 都是如此。因为 ASIST 的性格和与这个人的关系（me.md）、关于这个人的事实（user.md，比如过敏），不能只在发言的字词碰巧对上那个标题时才起作用，而必须在任何对话里都起作用。本人托付的事和被说希望避开的事写在 user.md 的“ASIST への期待”里，一直留到本人在对话中取消。页面和日记与以往一样，只检索与发言有关的内容附到对话里。me.md 和 user.md 不放进检索的索引，所以既不出现在对发言的注记里，也不出现在 recall 的结果里。因为对已经完整出现在每次对话里的文字再用检索附一次，只会让同一件事读两遍。

Gemini Live 的会话一旦恢复，就按最初打开时的系统提示词继续下去。因此 ASIST 会按用于恢复的句柄，分别记住该会话读过的 me.md 和 user.md。如果在记忆界面的保存中，或在已合入的整理中，这两个文件变了，下次打开会话时就不恢复，而是用带上当前两个文件的系统提示词和最近的对话重新打开。这两个文件一天最多变几次，所以不恢复而重新打开的麻烦很小。

两个文件各有 3000 token 的上限。文件越写越多会让每次对话变重，这个担心由这个上限来回应。token 按字符种类（假名、汉字、谚文、天城文、拉丁字母、数字与符号等）各自的权重估算。整理的 Agent 运行的地方不保证能跑真正的分词器，对话模型也因提供商不同而各有各的算法，所以整理的脚本和 ASIST 两边都用同一个轻量估算，它很少低于任何模型的计数。上限不按语言改变。因为估算带有按字符种类的权重，同一个上限下，每次的负担在任何语言里都大致相同。3000 token 在日语里大约相当于 4000 字，在英语里大约相当于 1800 词。

上限由写入的一方遵守。整理的技能里有一个计数的脚本和一个检查写法的脚本，Agent 在结束前运行这些脚本，一直缩到收进上限内为止。两个脚本用 Python 写，用 ASIST 随应用打包的 uv，在 ASIST 放进 userData 的 Python 上运行。因为用官方安装程序装了 codex 或 claude 的计算机上，可能既没有 Node 也没有 Python。ASIST 把随应用打包的 uv 复制到技能的文件夹里，Agent 则用路径指定那个 uv 来运行。因为 codex 用登录 shell 运行命令，claude 用读入本人 shell 配置的 shell 运行命令，于是 macOS 的 path_helper 或本人的配置文件会重排 PATH，本人的 uv 有时会比 ASIST 放在 PATH 最前面的文件夹更早被找到。只让 uv 使用那个 Python，也不让它下载，所以 Agent 的命令在没有网络的沙箱里也能运行。Python 由 ASIST 在启动 Agent 之前装好。ASIST 自身用 TypeScript 持有同一套规则，计数的数值放在两边都读的同一个文件里，规则用一组应当返回相同答案的示例来确认。ASIST 也用同样的计数，不把会留下超过上限的文件的整理合入，在记忆界面拒绝超过上限的保存，并显示多了多少 token、大约删多少字合适。把超过上限的文件带进对话时，不截断，完整带上。上限出现之前就已经很长的文件，在下次整理把它缩小之前，就那样带上。

不再持有以前的 `instruction.md`（总是记住的事）。ASIST 在打开记忆时，把它“私について”一节里的句子原样移到 me.md，其他节移到 user.md，然后删掉，做成一个提交。包括本人写下的句子在内什么都不会丢，移过来的节由下次整理收进各自的标题下。摘要写进 user.md 的摘要一节，其他节写进同名标题的节，所以不会出现两个同名标题，导致保存和整理都被拒。即使移到一半停下、下次启动再移一遍，同一句话也不会进去两次。

不持有用来遗忘记忆的工具和文件。真正想删掉的记忆，由用户在记忆界面删除。对话里被说“今の忘れて”的那件事，整理的 Agent 不写进日记和页面。对话里出现过的事是否留在记忆里本来就是概率性的，所以这样够了。

## 未采纳的方案

- **每次对话只带 instruction.md，user.md 和 me.md 靠检索取用。** 这是截至 2026-10-02 的决定，为的是避免文件越写越多让每次对话变重。但是像过敏这样的事实和 ASIST 的性格，在发言的字词没有对上标题的对话里起不到作用。这份重量可以用上限压住。
- **把 instruction.md 也和 me.md、user.md 一起带上。** instruction.md 的“この人について”和“私について”是 user.md 和 me.md 的摘要，所以同一个事实每次会带上两遍。在实际的记忆里，三个节的字符序列（连续的两个字符）有 84～91% 已经出现在 user.md 或 me.md 中，与无关的文章也有 24～42% 重合的情况相比，这几乎全是重复。剩下的“頼まれていること”本来就有 user.md 的“ASIST への期待”这个存放处。
- **把 instruction.md 内容的搬迁交给下次整理的 Agent。** Agent 就算漏掉句子，也没有察觉的手段。ASIST 把句子原样移过去就不会有损失，只有重新整理可以交给 Agent。
- **把随应用打包的 uv 放在 Agent 的 PATH 最前面，命令里叫 `uv`。** 起初是这么做的。登录 shell 里 PATH 被重排，本人的 uv 更早被找到。
- **在技能的文件夹里放一个指向随应用打包的 uv 的链接。** Windows 上无需权限就能创建的链接只有 junction，于是只能听任删除 worktree 的 git 决定是否连目标一起删。副本在 APFS 上不占空间，在其他地方也只是一天写一次 uv 而已。
- **用 node 运行整理的脚本。** 以前的 validate.mjs 就是这么做的。在没有 Node 的计算机上，Agent 无法确认自己写的东西，超过上限的整理全都会以不合入结束。
- **把真正的分词器随技能打包进来计数。** 光是 o200k 的词表就有数 MB，而且和 Claude、Gemini 的算法也不一样，不能说它比按字符种类的估算更正确。
- **把 UTF-8 的字节数除以 4 来估算。** 这是 ASIST 在其他地方用的估算，但它把印地语算成 o200k 的 1.5～2 倍，于是只有那种语言能写的量降到将近一半。
- **超过上限的文件按上限截断后带进对话。** 这会悄悄丢掉一部分记忆。
- **从对话里删除记忆的工具（`forget_memory`）和记录已删除内容的文件（`forget.jsonl`）。** 删除用记忆界面就够了。
- **只在记忆界面删除时才写进 `forget.jsonl`，以免被下次整理重新造出来。** 选择了让机制更简单。

## 实测

在 2026-10-02 测量。估算值与实际 token 数的比，用应用字典、说明文字和记忆的例句做成的 82 篇文章（对话的 11 种语言）来看，相对 o200k（OpenAI 和 gpt-oss）是日语 0.94～1.13、韩语 0.97～1.13、印地语 0.95～1.19、英语 1.07～1.27、其他拉丁字母的语言 0.94～1.21。相对 Gemini 3.8 Flash 的 countTokens，任何语言都在 0.94 以上（日语里 Gemini 的计数约为 o200k 的 0.8 倍）。Qwen3 的分词器把印地语算成这个估算的约 2.4 倍。Claude 的分词器没能测。实际使用中的三个日语记忆文件（1140～2463 字）里，估算是 o200k 的 1.01～1.02 倍。

从打开 Gemini Live（gemini-3.8-live）的会话到 setupComplete 到达的时间，各测 10 次取中位数：没有记忆 630 ms、instruction.md 大小的记忆（Gemini 里 688 token）634 ms、instruction.md、me.md、user.md 三个（3056 token）643 ms、把三个各加到接近 1500 token（3302 token）666 ms。都收在波动范围（540～770 ms）之内。同一天稍后重测，没有记忆 692 ms、三个（3056 token）662 ms、把两个各加到接近 3000 token（Gemini 里 4531 token）713 ms，这也在波动范围（626～1066 ms）之内。带上记忆也不会让打开变慢。

整理的 Agent 的命令（`<技能的路径>/uv run --no-project <技能的路径>/scripts/<脚本> .`）在没有网络、也写不进 Python 存放处的沙箱里的登录 shell（bash -l）中也能运行。在那个 shell 里，本人安装的 uv（`~/.local/bin/uv`）比放在 PATH 最前面的文件夹更早被找到。把 uv 复制到技能的文件夹花了 30～40 ms。安装 Python 只在首次，花了 67 秒，放进去 66 MB。已经装好时 `uv python install` 在没有网络的情况下 0.06 秒结束。`uv run` 首次 0.58 秒，从第二次起 0.06 秒（uv 0.12.18、Python 3.12.14、Apple 芯片的 Mac）。

## 已知限制

- 第一次整理之前要获取 Python，所以那时没有网络的话整理会失败，在第二天 0 点重试。
- 规则存在于 TypeScript 和 Python 两处，只改其中一边时，两边会一直不一致，直到共同的示例集测试失败。
- 移完 instruction.md 的内容之后，me.md 和 user.md 可能超过上限，在下次整理缩小它们之前，在记忆界面不把该文档缩到上限以内就无法保存。
- 即使在记忆界面删掉页面，如果那段话出现在尚未整理的日子的对话里，下次整理可能会把页面重新造出来。

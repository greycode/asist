# 在 Mac 上，按用户登录 shell 的 PATH 查找 Agent 的 CLI，并用同一个 PATH 启动

从 Finder 或 Dock 打开的应用，从 launchd 收到的 PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`。用 npm 安装的 codex 是以 `#!/usr/bin/env node` 开头的脚本，用这个 PATH 启动时找不到 node，以退出码 127 失败。nvm、bun、pnpm 在 `~/.zshrc` 里添加到 PATH 的文件夹中的 CLI，也根本找不到。因此 ASIST 把用户的 `$SHELL` 作为与打开终端时相同的交互式登录 shell 启动，读取 PATH，在该 PATH 的文件夹里查找 CLI，任务的 CLI 也用同一个 PATH 启动。查找和启动都由同一次回答决定，所以不会出现显示为已找到的 CLI 一启动却不能用这种错位。这个回答会保留到打开设置界面重新查找 CLI 为止。启动 shell 会让用户的设置每次都全部执行，所以其他设置改变时不重新查找。应用的状态不等待回答，在回答到来之前告知正在查找 CLI，回答到来后重新发送状态。这是因为对话和麦克风的开始要等待状态。shell 没有在时限内回答时，即使 CLI 在固定位置也显示为无法启动的状态，不启动任务。因为如果保持短 PATH 启动，npm 的 CLI 和 Agent 运行的命令都会以同样的方式失败。

## 未采纳的方案

- **在固定位置用 `zsh -lc 'whence -p'` 查找，启动时保持短 PATH。** 非交互的 zsh 不读 `~/.zshrc`，`$SHELL` 不是 zsh 的用户的设置也不读。找到的 CLI 用短 PATH 启动，所以用 npm 安装的 CLI 不能运行。
- **把需要解释器的脚本型 CLI 与 Windows 的 `.cmd` 一样当作无法启动而拒绝。** npm 是 codex 主要的安装方式之一，这样就等于拒绝它。
- **在 main 里同步向 shell 询问。** 有些用户的设置会花上数秒，其间 main 的所有处理都会停住。

## 实测

- 在 `~/.zshrc` 里加载 nvm 和 pyenv 的 zsh 用 `-i -l -c` 返回 PATH，在 Apple Silicon 的 Mac 上花了 0.55～0.7 秒（2026-10-02）。时间上限设为 10 秒。

## 已知限制

- 每次查找 CLI，用户的 shell 设置都会全部执行。该设置因错误中断，或超过 10 秒时，Agent 的任务不会启动。
- tcsh 和 csh 不接受 `-l` 与其他选项一起使用，所以只作为交互 shell 启动。因此不读取在 `~/.login` 里添加的 PATH。
- 创建任务的处理不等待 shell 的回答。因此从对话里委托的任务会在显示确认界面之前查找 CLI，启动不了就当场拒绝。因为如果批准之后任务马上失败，看起来就像批准没有成功。没有人批准的记忆的整理任务，在找不到 CLI 时，已启动的任务会因为这个原因失败。

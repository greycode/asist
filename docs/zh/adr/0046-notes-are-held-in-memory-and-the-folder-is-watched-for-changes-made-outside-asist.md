# 笔记放在内存里供搜索，ASIST 之外的改动靠监视笔记文件夹来合入

笔记服务在列表、搜索、读取 1 条中的任意一个第一次被调用时，读完整个笔记文件夹放进内存，之后就从那里回答。保存和删除时不读全部。ASIST 自己保存或删除的笔记，服务就改写当时持有的内容。用其他编辑器改过的笔记、在 Finder 或资源管理器里增删的笔记，服务靠监视文件夹（`fs.watch`）得知，重新读取文件并合入，只把有变化的笔记告诉界面。这是因为如果每次搜索都读整个文件夹，在笔记有 4 万条时，1 次搜索会超过 2 秒，`search_notes` 超时，模型就无法确认刚保存的笔记。另外，界面只在启动时读一次列表，所以 ASIST 之外增删的笔记要到下次启动才出现在列表里，在外面删掉的笔记也无法从列表里去掉。

在笔记界面上正在编辑的笔记被 ASIST 之外改写时，如果还什么都没改，就静默地把正在编辑的正文换成新内容。有未保存的编辑时，保留编辑，告知已在外部被改写，让用户选择是读入新内容（不核对编辑就丢弃），还是用正在编辑的内容覆盖。在选择之前无法保存，所以编辑不会在无人察觉的情况下覆盖外部改动。正在编辑的笔记在外部被删除时，如果有未保存的编辑就保留并告知，保存时会作为新笔记创建。笔记服务拒绝写不存在的笔记，所以不会用同一个 id 重新创建。如果什么都没改，就关闭编辑，显示最新的那条笔记。没有在编辑时发生的外部改动，就原样显示在列表和正文里。

## 未采纳的方案

- **每次搜索都读文件夹（以往的做法）。** 其他编辑器里的改动总是能看见，但笔记到几万条时搜索会超时。
- **先只查所有文件的修改时间，按新的顺序读，找到搜索上限的 10 条就停下。** 常见的词代价小，但命中的笔记少的词最终还是读完所有文件。
- **把告知外部改写之后的保存视为用正在编辑的内容覆盖。** 按下保存的人有没有读过提示，界面无从得知，所以就定成在选择之前无法保存。

## 实测

2026-10-02，在 Apple M5 上、因其他工作而负载很高的状态（load average 10～20）下，用 Electron 43 的 Node 读取生成的 4 万条笔记（平均 659 字节）来测量。

- 搜索 1 次：读文件夹的做法 0.85～7.8 秒，放在内存里的做法 16～40 ms。
- 第一次读整个文件夹的时间：1.7～2.6 秒。只在启动后界面读取列表时花 1 次。
- 放在内存里的量：堆约 28 MB。
- 在 ASIST 之外写入笔记，到把该改动发给界面：84～103 ms。
- 什么都没变时重新检查整个文件夹的时间（列表和逐文件的 stat）：0.25～0.46 秒。
- 把文件夹整体换成内容不同的副本时：重读 4 万条，到用 1 次发送（11 MB）送到界面，共 3.9 秒。

## 已知限制

- macOS 的 FSEvents 在漏掉通知时会用标志告知这一点，但 Electron 43 的 Node（libuv 1.52）会丢弃带这个标志的通知。漏掉的改动要到那条笔记下次变化，或者下次启动 ASIST 时才出现在界面上。
- 在 macOS 上，main 进程里任何地方每打开或关闭一次 `fs.watch`，libuv 都会在另一个线程里为进程重建一条 FSEvents 通知流。从 `fs.watch` 返回到那条流开始运行之间的短暂时间里，改动到不了任何监视。笔记文件夹的监视在第一次读笔记时打开，文件夹被换成别的文件夹时也不重新打开（FSEvents 按路径监视，所以替换后的文件夹的改动也会照样送达）。重新打开只发生在文件夹被换成指向其他位置的链接、实际路径变了的时候，以及监视失败的时候，之后重新检查整个文件夹。
- 在 Windows 上，监视接收通知的缓冲区（4 KB）溢出时会收到没有名字的通知，用短的 8.3 格式名字删掉笔记时通知里的名字不会是该笔记的名字，所以两种情况下都要重新检查整个文件夹。
- 读不了的笔记（例如没有读权限的）会从列表和搜索中排除并写进日志，其他笔记照常显示。试图读那条笔记时，会返回说明读不了原因的错误。

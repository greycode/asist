# live 引擎只采用连回复内容也自己决定的模型，不采用 GPT-Live

语音引擎的 live 里，只采用这样的引擎：除语音输入和朗读之外，连回复内容的判断和工具调用也由一个模型来做（现在是 Gemini Live）。像 GPT-Live 那样，语音模型负责听和说、把回复内容交给对话模型的这种分工的引擎，不采用。在 GPT-Live 里，语音模型交给对话模型的信号不带发言的句子，所以只能从转写到达的时刻去推测，某个请求针对的是哪条发言。推测一旦不准，发言就不会出现在界面上，或者不会传给对话模型。语音模型会把对话模型的句子换成自己的话读出来，所以听到的话和界面上的文字不一致；它也不告诉读到哪儿了，所以会话日志也无法根据转写来写。指令和费用也变成了语音模型与对话模型两套。这些都来自 API 不传达的信息，ASIST 这一侧改不了。

## 未采纳的方案

- **让 GPT-Live 原样读出对话模型写好的句子。** 声音和界面的不一致会变小，但分不清请求对应哪条发言这一点和两套费用仍然存在，而原本使用 GPT-Live 的理由——自然的说话方式——也会减弱。

## 已知限制

- 没有一种组合能一边用喜欢的对话模型（如 Claude），一边用可以中途打断的全双工语音说话。用喜欢的对话模型说话时使用 cascade，附和和打断由 ASIST 判断。

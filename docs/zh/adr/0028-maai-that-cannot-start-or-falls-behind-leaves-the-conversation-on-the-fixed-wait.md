# 无法启动 MaAI 或处理滞后时，用设置的静音长度继续对话，并把这件事只告知一次

在“声”界面上打开着 MaAI，但打开麦克风时无法启动 MaAI 的 worker（没有 Python 环境或模型、worker 已退出、加载没有在时限内结束）时，就不停掉麦克风，而是按设置的静音长度判断说完，继续对话。原因写进 main 的日志，对用户，则只在打开 MaAI 之后的第一次告知：无法启动 MaAI，正在按设置的静音长度判断。即使 worker 在运行，只要处理跟不上对话的声音、对说完的估计变成针对 500 ms 之前的声音，就不使用这个估计，在追上之前同样按设置的静音长度判断。这种旧估计连续 5 秒送来，并且其间滞后还扩大 500 ms 以上时，就在打开麦克风期间只告知一次：MaAI 的处理滞后，在追上之前按设置的静音长度判断。估计有 1 秒以上没有送来时，以及重新打开麦克风时，就重新计算持续的时间。

ASIST 定下的做法是不掩盖失败、不切换到别的行为，这里是一个例外。MaAI 是为了更快地判断说完，没有它也能对话。为了 MaAI 而停掉麦克风，对话本身就做不成了。另一方面，不告知就切换，用户会一直以为 MaAI 在运行，弄不清回应慢的原因。启动不了这件事，在用户修好之前每次打开麦克风都会同样发生，所以打开 MaAI 之后只告知一次。滞后由当时计算机的忙闲决定，所以每次打开麦克风都重新判断。把滞后正在扩大作为条件，是因为一度停住的 worker 在追赶的过程中，滞后会逐渐缩小。5 秒是按这样的长度选的：几秒就结束的负载下不会发出告知，负载持续时又会很快发出。从实测的 248 个来算，以实时 2/3 的速度均匀滞后的 worker，在负载开始后约 1.5 秒估计就会比 500 ms 旧，约 6.5 秒时发出告知。运行中的 worker 以短于 1 秒的间隔发送估计，所以估计中断 1 秒以上，就说明 worker 停了、被停掉了或者正在重新启动。那之后的估计滞后与中断之前的滞后没有关系。

## 未采纳的方案

- **让打开麦克风这个操作整个失败。** 在修好 MaAI 或在设置里关掉它之前，无法对话。
- **估计一变旧就立刻告知。** 因其他处理叠加而一度停住的 worker 几秒就能追上，等到发出告知时已经在用 MaAI 的估计，告知的内容就不符合实际。
- **只看旧估计持续的时间来判断。** 从实测的 63.8 ms 来算，在 Core i9-9900K 上，worker 停了 2 秒之后，要过 5.9 秒估计才回到 500 ms 以内。告知发出后 MaAI 马上追上，告知的内容就不符合实际。
- **每当麦克风的声音到达时，用距离最后一个可用的估计的时间来判断滞后。** 不再发送估计的 worker 也会被算成滞后，对于只是退出后正在重新启动的 worker，也会告知处理滞后。

## 实测

- 2026-10-02，在高负载的 Mac 上，把声音按实时送入的 worker 在 30 秒里送出了 248 个估计。估计之间的间隔最大为 401 ms，估计针对的最多也只是 7.5 秒之前的声音。
- 2026-10-02，在 Apple M5（内存 32GB）上，其他工作造成的负载平均值为 11～15 时，用与应用相同的 MaAI 和模型让 worker 运行 15 秒，1 帧的处理中位数为 42～43 ms、第 90 百分位为 51～54 ms，估计之间的间隔最大为 163 ms。warm-up 的第一个结果就发送 ready 时，紧接 ready 的估计针对的是 800 ms 之前的声音，从 ready 起 405 ms 之内超过了 500 ms。处理完 warm-up 之后再发送 ready 时，从第一个估计起滞后为 0 ms。负载平均值在 15 左右的另一次运行中，1 帧的中位数变成 196 ms，中途还让 worker 停了 2 秒，14 秒之内滞后到 8.08 秒，MaAI 丢弃积压的声音，回到 0.56 秒，之后又滞后下去。
- 2026-09-27，在 Windows 11 的 Core i9-9900K 上，1 帧的处理中位数为 59.8 ms、第 90 百分位为 63.8 ms、最大为 66.7 ms。

## 已知限制

- 对话途中 worker 退出、又无法重新启动时，只写日志，当场不告知。如果下次打开麦克风时的启动也失败，只有在还没有告知过的情况下才告知。
- 滞后只根据 worker 送来的估计判断。完全不再发送估计的 worker，不作为滞后告知。
- 对于一直滞后、既不再扩大也不缩小的 worker，不告知。
- 只有附和和点头的模型滞后时不告知。其间，附和只根据文字判断。
- MaAI 关闭时、用日语以外的语言对话时，不会启动，所以什么都不告知。

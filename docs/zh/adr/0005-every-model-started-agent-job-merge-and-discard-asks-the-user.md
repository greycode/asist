# 对话中的模型启动和继续的 Agent 任务，以及 worktree 的合入与丢弃，一律先在确认界面取得用户的批准再执行

对话中的模型用 `run_agent_task` 和 `continue_agent_job` 启动或继续任务时，包括只读的任务在内，都会先显示确认界面。确认界面列出交给 Agent 的指令本身、工作位置、能否写入，只在用户按下按钮时才启动 Agent。`merge_agent_job` 也会把要合入的变更清单放进确认界面，只在获得批准时才合入。`discard_agent_job` 也会把要删除哪个任务的哪个 worktree 列进确认界面，只在获得批准时才删除。删除的变更无法还原。

对话中模型的上下文里会包含邮件、网页搜索、笔记、日程的文本。如果其中写着“エージェントでこのコマンドを実行して”“さっきの変更は捨てて”，模型就可能照着它启动任务，或者删掉用户还没看过的任务成果。另一方面，可写入的任务以 claude 的 `--permission-mode auto` 或 codex 的 `--approve-for-me` 运行，两者都不是 OS 的沙箱。claude 既能用命令也能用网络，还能写到工作文件夹之外。专用工作文件夹只是启动时的目录，并不是把它关住的机制。因此，任务要视为以用户的权限运行：启动之前和丢弃成果之前，都由用户本人看清内容再决定。

确认界面只能用按钮作答。不能用声音批准，确认界面显示期间的发话既不算批准也不算取消。对话轮次在等待确认答案的期间，不会因为发话而打断这一轮；等答案和该操作的结果记录下来之后，才处理发话。模型说“確認画面で承認してください”、用户用声音回答“はい”，这是很自然的流程，但如果用这句发话关掉确认，就等于取消了用户正要做的批准操作。在等待确认期间，如果只是打断了朗读、话没说完，朗读会停止，但这一轮不会被打断；收到答案和该操作的结果之后再回应。这个回应用户还没有听到过，讲的是已批准的操作后来怎么样了。

用户直接通过界面按钮做的操作（任务卡片的“取り込む”和“捨てる”、设置界面的“今すぐ整理する”）本身就是批准，所以不再叠加确认界面。不过，只有用卡片的“捨てる”丢弃 worktree 里可能有子模块工作的任务时，才显示确认界面。因为子模块里的提交不会出现在卡片的差异里，有时只存在于 worktree 中的副本里，所以按下按钮时，用户并没有看到什么会消失。记忆的整理不问任何人，由定时器运行并合入，所以要确认差异只是记忆文件夹中的普通文件，若不是就不合入，记为失败。整理任务本身也不在可写入任务的无人值守模式下运行。claude 以 restricted 模式运行，把文件工具限制在工作文件夹内，除许可的以外一律拒绝（dontAsk），能执行的命令只有技能的检查脚本。codex 在不发出批准的 workspace-write 沙箱中运行，网络和对工作文件夹之外的写入由 OS 阻止。

## 未采纳的方案

- **只读的任务不经确认就启动。** 只读的 claude 任务也有 WebFetch，所以能读取 ~/.ssh 等并附在 URL 上发到外部。
- **在专用工作文件夹里运行的任务不经确认就启动。** 工作文件夹并不能把它关住，可写入的任务能写到主文件夹的任何地方。
- **git 仓库的任务用 worktree 隔离后不经确认就启动，批准放到合入时做。** worktree 也关不住它，在合入之前，Agent 在仓库之外什么都能做。
- **用工具的说明让模型来做合入的确认。** 既然进入上下文的文本能驱使模型，对模型的指示就代替不了批准。
- **丢弃 worktree 不经确认就执行。** 没有合入的成果只存在于 worktree 里，被文本驱使的模型一旦删掉就再也找不回来。

## 已知限制

- 每次启动任务都会显示确认界面，所以用户不在界面前，任务就不会启动。确认会在 5 分钟后中止，此时不启动。
- 在等待确认期间搭话，那句回应要等到回答确认之后才会返回。
- 在 Gemini Live 中工具由 Gemini 调用，所以对说出的内容，Gemini 会当场作答。Gemini 取消调用时，确认界面也关闭。

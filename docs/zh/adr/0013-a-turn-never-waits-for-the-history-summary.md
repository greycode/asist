# 对话轮次不等待历史摘要，上下文接近 API 上限时不回答，而是这样告知

历史摘要要读很长的对话、写很长的文本，所以有时要花几分钟，也会失败。对话轮次不等待这个摘要。上下文超过 20 万 token 时，摘要在这一轮之前开始，这一轮用当时的历史发送。超过接近 API 上限的 80 万 token 时，到摘要结束之前不发送这一轮，而是回答“正在生成摘要，请稍后再来搭话”，然后结束这一轮。这句话不是失败，而是作为应用的回复只显示并说出一次，并作为说过的话留在历史里。摘要在那期间也在后台继续，失败时由下一轮，或对话停着时的定期摘要重新开始。任务报告不会因这句话而被视为已送达；在摘要成功之前，它不会开始发送，等待期间也不消耗尝试次数。

## 未采纳的方案

- **接近上限时，这一轮等待摘要结束。** 摘要期间会沉默几分钟，摘要每失败一次，下一轮也照样要等。任务报告会被视为过了等待播放的时间仍未送到，于是被重发，同一份报告被说上好几遍。
- **削掉旧的轮次再发送。** 答案会回来，但用户看不出它忘了之前的话。这就等于悄悄降低质量。

## 已知限制

- 在摘要持续失败的期间，上下文接近上限的对话无法作答。

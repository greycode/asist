# 在 Mac 上，确认 Agent 已经结束，要看 CLI 的进程组、CLI 启动的进程、持有 token 的进程是否一样都不剩

claude 和 codex 会把 Agent 运行的命令，分别放在不同的会话或进程组里启动。claude 2.1.276 的 Bash 工具以 `detached` 启动 shell，codex 0.137.0 把命令放进自己的进程组。因此，即使 CLI 的进程组已经空了，命令也可能留下来继续往 worktree 里写。于是在 Mac 上，用两种方法找出进程组之外的 Agent 进程。一种是，在任务运行期间每 0.5 秒读一次进程列表，按父 pid 追溯 CLI 的子孙进程，连同启动时刻一起记住。在别的会话里运行的命令，只要 CLI 还在运行就仍是 CLI 的子进程，所以能在 CLI 结束、变成 launchd 的子进程之前记住。另一种是，找出环境里带有 token 的进程，这个 token 由 ASIST 每次启动时放进环境变量 `ASIST_AGENT_EXECUTION_ID`。停止时，向 CLI 的进程组、记住的子孙中还在运行的，以及持有 token 的进程发送信号，当哪个都不剩时，就认为任务已经结束。CLI 自己结束时留下的进程也同样先停掉，然后再提交或清理 worktree。没能停干净的停止，再请求一次就会重新发送信号。

只有其中一种不够。Apple 在系统完整性保护下发布的 `/bin/zsh`、`/bin/sh`、`/bin/bash`、`sleep`、`cat` 等不会把环境暴露给 `ps`，所以用 token 找不到（macOS 26.2，2026-10-02）。claude 和 codex 用这样的 shell 运行命令，所以只看 token 会漏掉最常见形式的命令。另一方面，在读完列表之前父进程就已经结束的进程，顺着父进程也找不到，只能用 token 找到。

## 未采纳的方案

- **只看 CLI 的进程组。** 移到别的组的命令不计入，就会在没有停掉它们的情况下提交或删除 worktree，应用退出也照样放行。
- **只用 token 找。** Apple 发布的 shell 和命令的环境读不到，用 `/bin/zsh -c` 运行的循环之类的命令就会留下。
- **在停止时追溯父子关系。** CLI 先结束的话，剩下的命令会变成 launchd 的子进程，就追不到了。所以在任务运行期间先记下来。

## 实测

- 停止期间的一次确认花了约 45 ms。进程列表约 10 ms，用户所有进程的环境约 25 ms，重新读取在那里找到的进程约 10 ms（Apple M5，724 个进程中属于用户的 514 个，2026-10-02）。因为在 main 的线程里读，所以比 CLI 进程组的确认（每 25 ms）间隔更大，每 500 ms 读一次。任务运行期间的列表，读取时不阻塞 main 的线程。

## 已知限制

- 重启之后的回收中，子孙进程已经是 launchd 的子进程，追不到，所以进程组之外只用 token 找。Apple 发布的 shell 和命令即使还留着也找不到。它们留在进程组里时，无法确认 token，于是不停止并给出原因。
- 在读列表的 0.5 秒之间父进程结束的进程里，Apple 发布的 shell 和命令用两种方法都找不到。
- 子孙进程按启动时刻区分，但 `ps` 输出的启动时刻是本地时间，任务期间 Mac 的时区一变，就会丢失记住的子孙进程。
- 像 Agent 在任务里启动后留下的开发用服务器这样自己不会结束的进程，也会在任务结束时停掉。

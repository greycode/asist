# Google 的 OAuth 客户端从构建环境装入，而不是从仓库

用于登录 Google 的 OAuth 客户端 ID 和密钥不放进仓库。分发的应用里，把构建时的环境变量 `ASIST_GOOGLE_CLIENT_ID` 和 `ASIST_GOOGLE_CLIENT_SECRET` 嵌入 main 进程；CI 里只把它传给用仓库 secret 构建应用的任务。从仓库运行时，用同样的名字写进 `.env`。安装型应用的密钥，Google 自己就把它当作无法保密的东西，但仓库是公开的，写进去的话任何人都能以 ASIST 的名字弹出同意界面，用掉项目的次数上限。从构建环境装入的话，重建客户端时也只要换掉 secret 就行。

没有装入客户端就构建的应用照样能启动，也能显示日历界面。第一次使用日历时，报一个说明没有客户端的错误。分发的应用由 Mac 的 `npm run release` 和 Windows 的发布工作流先确认客户端存在再构建，所以用户不会看到这个错误。

## 未采纳的方案

- **没有客户端就停止启动。** 连不用日历的开发者，也会在写进 `.env` 之前一直无法运行应用。
- **在没有客户端的构建里隐藏日历。** 忘写 `.env` 时日历会悄悄消失，不容易察觉原因。而且，仅仅为了构建配置的差异，界面和工具的区分显示也要保留下来。

## 已知限制

- 从分发出去的应用的内部可以取出客户端 ID 和密钥。Google 的审核对安装型应用就是以此为前提的。
- 来自 fork 的拉取请求的 CI 拿不到 secret，所以那种构建里不会装入 Google 的客户端。
